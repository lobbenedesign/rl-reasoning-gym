# Changelog

## Unreleased

### Added
- **Verifiable code-execution reward (RLVR-style)**: `src/code_execution_reward.ts` + `src/code_exec_worker.ts`, wired into `src/reward_models.ts` (`evaluateGroup` now accepts optional `codeTestCases`) and `src/grpo_trainer.ts`/`server.ts` (`POST /api/train/step` accepts a `codeTestCases: [{input, expectedOutput}]` array). Gap identified against real frameworks this project is conceptually adjacent to: HuggingFace TRL's `GRPOTrainer` supports pluggable `reward_funcs`, and open-r1 ships a `code_reward` function that actually executes candidate code against unit tests. Before this change, `RewardModelEngine.evaluateGroup()` only checked whether `expectedAnswer` appeared as a substring of the response — no code was ever run, so accuracy reward could be gamed by wording alone and had no relationship to whether the code actually worked.
  - Extracts the first fenced code block from a completion, executes it in an isolated Bun Worker (same sandboxing pattern as the `reasoning-tree-mcts` sibling project: hard timeout, `Bun.Transpiler` for TS stripping, `new Function()` execution, worker `terminate()` on timeout) against every supplied test case, and reports the real `testsPassed/totalTests` pass rate as `accuracyReward`.
  - Verified end-to-end against a live local Ollama instance (`granite3-dense:2b`): a 3-candidate GRPO step for "write a `double(x)` function" produced 3/3 candidates each passing all 3 real test cases. A control run asserting a deliberately wrong expected value (`triple(2) === 999`) correctly scored `accuracyReward: 0`, with the real execution log (`expected 999, got 6`) proving the reward comes from genuine execution, not from guessing or hardcoding.
  - `RewardModelEngine.evaluateGroup()` is now `async` (it awaits real sandbox execution when `codeTestCases` are supplied); callers updated accordingly.
- **Procedural verifiable tasks, reasoning-gym style**: new `src/tasks.ts`. Gap identified against `open-thought/reasoning-gym`, the real project this repo's name echoes: it ships 100+ procedurally-generated task datasets across domains with a programmatic `score_answer` verifier and a documented cascade scorer (exact → numeric → lenient fallback). This repo previously had one way to pose a task (free-text prompt + substring match), which had a real demonstrable false-positive bug (`"6"` is a substring of `"16"`, so a wrong answer scored as correct) and a false-negative problem (a correct number phrased differently could fail).
  - Added three procedurally-generated, seeded (mulberry32 PRNG) task types with real ground truth computed in code and real programmatic verifiers: `arithmetic_word_problem`, `string_manipulation`, `list_logic`. New endpoints `GET /api/gym/tasks` (list types) and `POST /api/gym/generate {taskType, seed}` (generate a reproducible instance).
  - Added `cascadeScore()`: exact trimmed match → numeric equivalence (scans every number in the response) → substring fallback. Wired into `reward_models.ts` for every non-code accuracy check (`codeTestCases` path is untouched and still uses real execution).
  - Verified: `cascadeScore("The final answer is 16.", "6")` → `correct:false` (false positive fixed); `cascadeScore("...totale finale e = 42 unita.", "42")` → `correct:true` (formatting false negative fixed); a live seed-42 `arithmetic_word_problem` (30×12=360) scored `granite3-dense:2b` candidates with `accuracyReward:1, verification.method:"numeric"`.
- **Multi-round GRPO loop with real few-shot self-refinement**: new `src/multi_round_trainer.ts`, wired into `POST /api/train/multi-round`. Still no gradient/optimizer/checkpoint — a prompt-space loop that runs `rounds` real sequential GRPO steps on the same task and feeds the real highest-reward response from round *i* back as a one-shot example for round *i+1*, but only when that response scored a real positive accuracy reward. `grpo_trainer.ts`'s `runStep()` gained an optional `fewShotPreamble` parameter to support this.
  - Verified with an honest negative result, reported as-is rather than cherry-picked: a 3-round run (`granite3-dense:2b`, seed 123, `string_manipulation` reverse task, expected `"enoizator"`) had the model answer `"etenaror"` (wrong) in all 3 rounds; `meanRewardByRound` stayed flat at `[0.5, 0.5, 0.5]` and `monotonicallyImproved` correctly reflects that no real gain occurred — because the model never scored a real accuracy point, no few-shot example was ever injected.

## v1.0.0 — Honest audit / real GRPO rewrite
See commit `4f24ea2` ("Audit onesto: sostituisce il GRPO finto con generazione reale via Ollama, rimuove il benchmark competitor inventato") and the README's "What this project IS and IS NOT" section: earlier versions used `Math.random()` for advantages, fixed multiplier formulas instead of real test-case scoring, and an invented "vs Top 5 Competitors" comparison table with numbers that were never measured. Those were removed. This release replaced them with real Ollama-sampled completions, deterministic verifiable reward functions, and the exact GRPO group-relative advantage formula computed over real rewards — while explicitly documenting that no gradient update, optimizer step, or checkpoint write ever happens here.
